# Роли и админ-панель — описание фичи

## О чём фича

После модуля 7 у каждого пользователя свой аккаунт и свои транзакции.
Но владелец приложения (я, разработчик) никак не управляет
пользователями: не вижу, кто зарегистрировался, не могу заблокировать
спамера, не могу удалить аккаунт нарушителя.

Добавляем **систему ролей** — `user` и `admin` — и **админ-панель**,
чтобы:

- у владельца проекта (моего email) была роль `admin`;
- админ видел список всех зарегистрированных пользователей;
- админ мог **заблокировать** пользователя (запретить вход и доступ к данным);
- админ мог **удалить** пользователя (вместе с его транзакциями);
- обычный пользователь (`user`) **не мог** попасть в админ-панель — даже
  по прямой ссылке.

## Технический стек (май 2026)

- **Next.js 16** (App Router) + TypeScript — уже есть из модулей 6–7
- **Supabase Auth** — продолжаем использовать встроенную систему
- **`@supabase/ssr`** — клиенты для браузера и сервера (уже есть)
- **Service Role Key Supabase** — нужен **только на сервере**, чтобы
  админ мог управлять чужими аккаунтами через `supabase.auth.admin.*`
  (этот ключ **никогда** не попадает в браузер)
- **Row Level Security (RLS)** — добавляем политики для роли `admin`,
  чтобы он мог читать чужие данные (но обычный пользователь — нет)
- **shadcn/ui** — `Table`, `Badge`, `AlertDialog`, `DropdownMenu`
  для админ-панели

## Главные функции

### 1. Таблица `profiles` с ролью пользователя
- Создаём таблицу `profiles`, связанную 1-к-1 с `auth.users`:
  - `id` (uuid, PK, FK → `auth.users.id`)
  - `email` (text, дублируем для удобного отображения)
  - `role` (text, `"user"` или `"admin"`, по умолчанию `"user"`)
  - `is_blocked` (boolean, по умолчанию `false`)
  - `created_at` (timestamptz, auto)
- Триггер на `auth.users`: при `INSERT` нового пользователя
  автоматически создаётся строка в `profiles` с ролью `"user"`
- Email админа задаётся в переменной окружения `ADMIN_EMAIL`
  (мой email — впишу в `.env.local` и в Vercel)
- Миграция один раз проставляет `role = 'admin'` для строки,
  где `email = ADMIN_EMAIL`

### 2. Защита админ-маршрутов через middleware
- Все URL вида `/admin/**` доступны **только** если в `profiles`
  у текущего пользователя `role = 'admin'`
- Если зашёл `user` (или гость) — редирект на `/` с тостом
  «Доступ запрещён»
- Проверка делается в `src/middleware.ts` через server-клиент
  Supabase (никаких клиентских проверок — это небезопасно)

### 3. Страница `/admin/users` — список пользователей
- Таблица со всеми зарегистрированными пользователями:
  - Email
  - Роль (`Badge`: admin — синий, user — серый)
  - Статус (`Badge`: активен — зелёный, заблокирован — красный)
  - Дата регистрации
  - Количество транзакций (опционально)
  - Колонка действий: «⋯» → `DropdownMenu` с пунктами «Заблокировать /
    Разблокировать», «Удалить»
- Сам админ в списке тоже виден, но **кнопки действий над собой
  скрыты** (нельзя случайно удалить себя)
- Пустого состояния практически не бывает (как минимум есть сам админ)

### 4. Блокировка / разблокировка пользователя
- В `profiles` меняем `is_blocked` на `true` / `false`
- Server Action `toggleUserBlock(userId)` в `app/admin/actions.ts`
- Перед действием — `AlertDialog` с подтверждением
- При входе заблокированного пользователя middleware проверяет
  `is_blocked = true` и сразу делает `signOut()` + редирект на
  `/login?reason=blocked` с сообщением «Аккаунт заблокирован»
- RLS-политика на `transactions`: заблокированный не может ни читать,
  ни писать свои данные (`is_blocked = false` обязательно)

### 5. Удаление пользователя
- Удаляет аккаунт полностью: запись в `auth.users` + все его транзакции
- Server Action `deleteUser(userId)` использует **Service Role Key**
  через `supabase.auth.admin.deleteUser(userId)`
- Каскад: на `transactions.user_id` стоит `ON DELETE CASCADE` →
  транзакции удаляются автоматически
- Запись в `profiles` тоже удалится каскадом (FK → `auth.users.id`)
- Двойное подтверждение: `AlertDialog` с вводом слова «УДАЛИТЬ»
- Нельзя удалить себя (проверяем `userId !== currentUser.id`)
- Нельзя удалить другого админа (на будущее, если их станет несколько)

### 6. Видимость админа в обычном UI
- В шапке приложения, если `role === 'admin'`, появляется ссылка
  «Админка» рядом с «Выйти»
- Обычный пользователь этой ссылки не видит и не знает о ней
- На дашборде транзакций админ видит **только свои** транзакции
  (админка — отдельный экран, чтобы не мешать обычной работе)

## Структура базы данных (что добавится)

### Таблица `profiles`

| Поле          | Тип               | Обязательное | Описание                              |
| ------------- | ----------------- | ------------ | ------------------------------------- |
| `id`          | `uuid`, PK, FK    | Да           | Ссылка на `auth.users.id`, `CASCADE`  |
| `email`       | `text`            | Да           | Email (дублируется из `auth.users`)   |
| `role`        | `text`            | Да           | `"user"` (default) или `"admin"`      |
| `is_blocked`  | `boolean`         | Да           | По умолчанию `false`                  |
| `created_at`  | `timestamptz`     | Да, auto     | Когда профиль создан                  |

### RLS-политики на `profiles`

- `SELECT`: `auth.uid() = id` ИЛИ роль текущего пользователя `= 'admin'`
  (свой профиль вижу я; все профили — только админ)
- `INSERT`: запрещён напрямую — только через триггер на `auth.users`
- `UPDATE`: только админ может менять `role` и `is_blocked`
- `DELETE`: запрещён напрямую — только каскадом при удалении из `auth.users`

### Обновлённые RLS на `transactions`

К политикам из PRD-2 добавляем условие «пользователь не заблокирован»:

- `SELECT`: `auth.uid() = user_id` И `is_blocked = false` в `profiles`
- `INSERT` / `UPDATE` / `DELETE`: то же условие
- Дополнительная политика для админа:
  - `SELECT`: админ видит все транзакции **только в админ-панели**
    (через специальную view или server-action, использующий
    Service Role Key, чтобы не «портить» обычные запросы)

### Триггер на `auth.users`

```sql
-- при создании нового пользователя автоматически создаём профиль
create or replace function public.handle_new_user()
returns trigger as $$
begin
  insert into public.profiles (id, email, role)
  values (
    new.id,
    new.email,
    case when new.email = current_setting('app.admin_email', true)
         then 'admin' else 'user' end
  );
  return new;
end;
$$ language plpgsql security definer;
```

## Чего НЕ делаем в этой версии

- **Несколько админов и управление ролями из UI** — пока только
  один админ, заданный через `ADMIN_EMAIL`. Повышать кого-то до
  админа из интерфейса нельзя
- **Логи действий админа (audit log)** — не пишем кто и когда
  кого заблокировал. Полезно, но в следующую итерацию
- **Soft delete / архив пользователей** — удаляем сразу и насовсем
- **Восстановление пароля админом за пользователя** — пользователь
  делает это сам через стандартный flow Supabase
- **Email-уведомление пользователю о блокировке / удалении** —
  пока без писем
- **Поиск, сортировка, пагинация в списке пользователей** —
  при росте базы добавим, для старта хватит простой таблицы
- **Просмотр транзакций любого пользователя в админке** —
  админ видит только список людей, не их данные (приватность)

## Дополнительные правила безопасности

- **Service Role Key** живёт **только** в `lib/supabase/admin.ts`
  и используется **только** в Server Actions внутри `app/admin/**`.
  Никаких импортов из `'use client'` компонентов
- Перед каждой админской операцией повторно проверяем роль через
  серверную сессию — `middleware` это не финальная защита,
  а первый барьер
- Проверка «не сам себя удаляю / не другого админа» дублируется
  на стороне Server Action — клиент мог бы прислать любой `userId`
- Все Server Actions админки валидируют входной `userId` через `zod`
  (это должен быть валидный uuid)
- После любой операции, меняющей данные — `revalidatePath('/admin/users')`
- Никогда не показываем в UI и в логах Service Role Key и
  внутренние идентификаторы Supabase (только email и публичный `id`)
